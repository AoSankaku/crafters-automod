# Stop Forum Spamによる追加の警戒

この機能は、最近のSFS一致情報をアカウントの追加調査に使います。SFSの掲載だけでロール付与・凍結・削除はしません。通常の本文ルールとは独立したT3の観察材料で、人間の判断を優先します。

## 有効化

既定は無効です。`.env`またはsystemd環境ファイルへ設定し、ビルド・再起動します。

```ini
SFS_ENABLED=true
SFS_CHECK_IP=false
```

`dry-run`でも`SFS_ENABLED=true`なら外部への照会は行います。Misskeyへの自動制裁は既存どおりdry-runで抑止されます。実ユーザー情報を外部へ送りたくない環境では`SFS_ENABLED=false`を維持してください。

メールはMisskeyの`admin/show-user`が返す**確認済み**アドレスだけを使います。アドレスを前後trim・小文字化してMD5の`emailhash`で照会し、平文メール・ノート本文・ユーザー名はSFSへ送りません。ハッシュは匿名化ではなく、SFS側で照合可能な識別子です。ハッシュ照会ではSFS側のメール正規化・別名処理が働かないため、Gmailの別名等を取りこぼす可能性があります。[SFS公式API仕様](https://www.stopforumspam.com/usage)

IP照会も必要な場合に限り、`SFS_CHECK_IP=true`を指定します。Misskeyの専用`admin/get-user-ips`が返す直近90日以内の公開IPを最大1件、平文のIP値としてHTTPSで送信します。共有IPの誤検知に配慮し、IPだけでも自動制限しません。失敗ログインのIP、プライベート・ループバック・文書用・予約アドレスは照会しません。IP取得には追加の管理者権限`read:admin:user-ips`が必要で、通常のモデレータートークンでは利用できません。IP取得ができなくても確認済みメールのチェックは継続します。権限を自動で引き上げる処理はありません。[Misskey公式実装](https://github.com/misskey-dev/misskey/blob/develop/packages/backend/src/server/api/endpoints/admin/get-user-ips.ts)

## 警戒の基準

基準は人間向け`rules.md`から`rules.generated.json`の`accountReputation`へ静的生成します。実行時に自然言語を解釈したりLLMを呼んだりしません。生成物はT3だけを許可し、T1/T2の指定や未知の設定を拒否します。

| 条件 | 既定値 |
|---|---|
| 最終報告からの経過 | 90日以内 |
| 報告回数 | 3回以上 |
| SFS confidence | 75以上 |
| メールの一致 | 警戒点40 |
| IPの一致 | 警戒点20 |

有効な一致があればT3として監査・遅延レビューへ送り、`riskScore`と種類別の集約情報を記録します。confidenceはSFSの指標であり、本人がスパマーである確率とは扱いません。古い・少数・低信頼の情報は加点しません。SFSのドメイン・ネットワークのワイルドカード判定は`nobadall`で無効にします。

`enforce`では、このT3の判定理由と「制限なし・レビュー予約」をMisskeyのモデレーションノートにも既定で追記します。メール・IP・照会ハッシュは転記しません。`read:admin:show-user`と**Manage moderation note**（`write:admin:user-note`）が必要です。dry-runでは追記しません。[記録と重複防止の設定](../README.md#misskeyから判定ログを確認する)を参照してください。

既存のT1はSFSを待たずに処理します。既存のT2/T3も先に処理し、SFSは監査へ情報を追加します。SFSの一致でT2/T1へ昇格させたり、既存の重大度を下げたりしません。本文ルールに一致しない投稿者も確認対象になります。登録直後の全アカウント走査ではなく、ローカルタイムラインで受信した投稿が契機です。

## 保存・分散・障害時の動作

キューへ入れるのはバージョン付きの候補IDだけです。メール、IP、メールハッシュ、本文、管理APIの全応答はDB・監査・ログへ残しません。保存するのはSFS結果の状態、警戒点、報告回数、confidence、最終報告時刻、ユーザーID・ケースIDです。既存の一般監査についても本文・トークンを保存しない方針を維持します。

SQLite単体と共有PostgreSQLの両方で、ユーザー・ポリシーごとのキャッシュを使います。SFS確認後は同一ユーザーの再照会を抑え、同じキャッシュを使ったT3レビューを投稿ごとに重ねません。確認済みの通常投稿は受信側でキューへの追加も省きます。キャッシュは既定6時間、最大1万行で、期限切れの結果は再利用せず、古い行を順次削除します。

SFSの予算はMisskey APIと別に、同じnamespaceの全プロセスで共有します。最小間隔とUTC日単位の上限をDB時刻で管理し、429/503の`Retry-After`を最大1時間の共有待機として保存します。指定がなければ60秒です。予算が空いていない場合はワーカーを長時間占有せず、未確認として扱います。上限はこのプロジェクトの保守的な既定値で、SFSの契約上限を保証する値ではありません。同じ送信元を他のサービスも使う場合は合算して調整してください。

| 環境変数 | 既定値 | 意味 |
|---|---|---|
| `SFS_ENABLED` | `false` | 外部照会を有効にする |
| `SFS_CHECK_IP` | `false` | 追加のIP照会を許可する |
| `SFS_MIN_INTERVAL_MS` | `1100` | SFS予算取得の最小間隔 |
| `SFS_MAX_DAILY_REQUESTS` | `5000` | namespace全体の日次予算 |
| `SFS_CACHE_TTL_MS` | `21600000` | 通常結果の再利用期限 |
| `SFS_FAILURE_TTL_MS` | `300000` | 照会失敗・未確認結果の再利用期限 |

タイムアウト、エラー、不正応答、予算不足は`unavailable`として記録し、「安全」とは判断しません。既存の静的判定は継続し、再利用期限後の次回投稿で再照会します。人間の判断、既存の凍結、管理者・モデレーターは照会・追加レビューより優先します。API待機でアカウント情報が古くなった場合も外部へ送信せず未確認に戻します。Misskey管理画面と完全に原子的な連携ではないため、人間が処置する前には共有オーバーライドを登録してください。

`/health`の`reputation`で有効状態、キャッシュ行数、累計予算取得数、当日の予算取得数、待機期限を確認できます。監査の`reputation.assessed`には状態・警戒点・集約情報があります。SFSの照会結果が陰性でも無害であることを保証しません。

## 更新と検証範囲

ルール変更時は既存の配置ガイドどおり受信を止め、旧設定のケースを処理してから全プロセスを同じルール・環境設定へ更新します。SFSのキャッシュと予算もSQLiteからPostgreSQLへの停止移行で引き継ぎます。既存の有効なDBには新しいテーブルを自動追加します。

公式APIの仕様を確認し、架空の`example.invalid`メールのハッシュで正常応答を確認しています。実ユーザーの情報は検証で送信していません。実Misskeyでの権限・応答形式・本番負荷、SFSの実際の掲載ユーザーでの陽性判定は未検証です。陽性・失敗・競合は固定応答を用いたテストで確認しています。LLMレビュー・過去投稿全削除のワーカーは引き続き未接続です。
